# BobiVPN Checker — план разработки

Переписывание проверщика VPN-ключей на **Go + Xray-core**, запуск в **GitHub Actions**.
Формат вывода — совместимый с текущим `studious-umbrella-main`.

Дата составления: 2026-07-26

---

## 0. TL;DR

Текущий проверщик (`scripts/vpn_checker.py`, Python + sing-box) выдаёт ~5200 «рабочих»
ключей, из которых реально пригодна малая часть. Основные причины — выключенная проверка
TLS, засчитывание HTTP-403 как успеха, неприменяемый порог скорости, гонки SOCKS-портов и
полное отсутствие памяти между прогонами.

Новый чекер: Go, **Xray-core как библиотека** (без процессов и портов), многоступенчатый
пайплайн со строгими критериями, историческая репутация ключей между прогонами,
шардирование в CI. Один статический бинарь — чтобы позже его можно было запустить локально
без изменений.

## 2. Почему Xray-core, а не sing-box

Распределение параметров в текущем выхлопе:

```
flow=xtls-rprx-vision   2297  (44%)   — XTLS Vision, референс — Xray
security=reality        2680  (52%)
type=raw                 398          — Xray-нейминг transport (tcp → raw)
```

Протоколы в локальных источниках (`myvpnkey/*.txt`): `vless` 6011, `ss` 347,
`trojan` 60, `vmess` 50. **Hysteria2 / TUIC / AnyTLS — 0 штук.**

Итог: 99.8% пула — это ровно то, что Xray поддерживает нативно и лучше всех.

### 2.1 Что теряем

Xray-core **не поддерживает** `hysteria2://`, `hysteria://`, `tuic://`, `anytls://`.
В текущем выхлопе это 12 ключей из 5196 (0.2%).

**Решение:** на стадии 0 такие ключи отсеиваются с явной пометкой `unsupported_protocol`
и счётчиком в отчёте. Интерфейс движка (`internal/engine.Engine`) делается абстрактным,
чтобы позже можно было добавить второй бэкенд (sing-box) для этих протоколов,
не трогая пайплайн.

## 3. Архитектура

### 3.1 Ядро: Xray-core как Go-библиотека

Главное архитектурное решение. Вместо `xray run -c config.json` в подпроцессе —
встраивание core прямо в бинарь:

```go
import (
    "github.com/xtls/xray-core/core"
    "github.com/xtls/xray-core/infra/conf/serial"
    xnet "github.com/xtls/xray-core/common/net"
    _ "github.com/xtls/xray-core/main/distro/all"   // регистрация всех протоколов
)

// Node → JSON (только outbounds, БЕЗ inbounds) → core.Config
cfg, err := serial.LoadJSONConfig(strings.NewReader(jsonCfg))
inst, err := core.New(cfg)
inst.Start()
defer inst.Close()

dest := xnet.TCPDestination(xnet.DomainAddress("cp.cloudflare.com"), xnet.Port(443))
conn, err := core.Dial(ctx, inst, dest)   // net.Conn через прокси
```

Дальше `conn` заворачивается в `http.Transport{DialContext: ...}` — и весь пайплайн
работает обычным `http.Client`.

**Что это даёт:**

| | Подпроцесс + SOCKS | Библиотека |
|---|---|---|
| SOCKS-порты | нужны, возможны гонки (дефект #6) | **не нужны вообще** |
| Ожидание готовности | `sleep(3)` наугад | `core.Start()` вернул `nil` |
| Оверхед на ключ | fork/exec + бинарь | ~5–15 МБ RAM, освобождается сразу |
| Точность таймингов | +погрешность SOCKS-хопа | замер прямо на `Dial` |
| Внешние зависимости в CI | скачать/распаковать Xray | **нет, всё в бинаре** |
| Windows | отдельный бинарь, пути | работает как есть |

Последний пункт важен для будущего локального запуска (см. §10).

Конфиг для библиотечного режима — минимальный, один outbound на инстанс:

```json
{
  "log": { "loglevel": "none" },
  "outbounds": [ { "tag": "proxy", "protocol": "vless", "settings": {...}, "streamSettings": {...} } ],
  "routing": { "domainStrategy": "AsIs" }
}
```

Домен назначения передаётся ноде как домен (не резолвится локально) — заодно
проверяется DNS самой ноды.

### 3.2 Запасной режим: подпроцесс

Флаг `--engine=subprocess` — генерируем батч на ~200 ключей: N SOCKS-инбаундов,
N аутбаундов, правила `inboundTag → outboundTag`.

**Важная деталь Xray:** непопавший ни под одно правило трафик уходит в **первый**
outbound. Поэтому первым в списке ставится `blackhole`, а прокси идут после него:

```json
{
  "inbounds":  [ {"tag":"in-0","listen":"127.0.0.1","port":30000,"protocol":"socks",
                  "settings":{"auth":"noauth","udp":true},"sniffing":{"enabled":false}}, ... ],
  "outbounds": [ {"tag":"blackhole","protocol":"blackhole"},
                 {"tag":"out-0", ...}, ... ],
  "routing": { "domainStrategy":"AsIs",
               "rules":[ {"type":"field","inboundTag":["in-0"],"outboundTag":"out-0"}, ... ] }
}
```

Режим нужен для отладки, воспроизведения багов на конкретном ключе и как страховка,
если Go API xray-core сломается после обновления.

### 3.3 Версия Xray

- Библиотека: `github.com/xtls/xray-core` — **пин точной версии в `go.mod`**,
  обновление через Renovate/Dependabot + прогон смоук-тестов.
- Бинарь для `--engine=subprocess`: последний релиз тянется в CI через GitHub API
  (`/repos/XTLS/Xray-core/releases/latest`), с фолбэком на пиннутую версию.
- Проверка версии на старте: `xray version` / `core.Version()` пишется в отчёт.

### 3.4 Структура репозитория

```
cmd/checker/main.go            режимы: collect | check | publish | selftest
```

## 4. Пайплайн проверки

### Стадия 0 — нормализация и дедуп *(снимает ~60% работы)*

- Парсинг в каноническую `Node`, **URL-декодирование всех query-параметров**
  (`path=%2Fws` → `/ws`).
- **Отпечаток (fingerprint)** = SHA-256 от
  `protocol|server|port|auth|transport|sni|host|path|flow|security|pbk|sid|method`
  — **без `#имени`**. Дедуп по нему.
- Резолв домена → набор IP (DoH с кэшем), дедуп по резолвнутому эндпоинту.
- Отсев заведомого мусора:
  - битый UUID, порт 0 или > 65535;
  - приватные / зарезервированные / loopback IP;
  - `security=reality` без `pbk` или с `pbk` неверной длины (43 символа base64url);
  - `sid` не hex или длиннее 16;
  - неподдерживаемый метод Shadowsocks;
  - **`flow=xtls-rprx-vision` при `security=none`** или с ws/grpc-транспортом → невалидно;
  - VMess с `aid > 0` (Xray работает только с VMessAEAD) → пометка `legacy_vmess`;
  - `hysteria2`/`hy2`/`hysteria`/`tuic`/`anytls` → `unsupported_protocol`.
- Финальная валидация: сборка Xray-конфига и `core.New()` без `Start()` —
  что core не принял, дальше не идёт (аналог `xray run -test`, бесплатно отсекает
  весь класс `parse_error`).

### Стадия 1 — дешёвый L4-фильтр

- TCP-dial с таймаутом **3 с** напрямую с раннера.
- Результат кэшируется по `IP:port` — мёртвый эндпоинт хоронит все ключи на него разом.
- Для доменов за CDN (Cloudflare/Fastly/Gcore диапазоны) стадия неинформативна →
  помечается `l4_inconclusive` и ключ пропускается дальше без отсева.

### Стадия 2 — настоящая проверка прокси ⭐

Через `core.Dial`, **с включённой проверкой TLS-сертификата на стороне чекера**:

1. `https://cp.cloudflare.com/generate_204` → требуем **строго `204` и пустое тело**.
   Не 200, не 403, не редирект.
2. `https://www.gstatic.com/generate_204` → то же самое.
   Два разных ASN обязаны ответить — ловит частичную блокировку.
3. `https://cloudflare.com/cdn-cgi/trace` → одним TLS-верифицированным запросом
   получаем **exit IP + colo + признак WARP**.
4. **Exit IP обязан отличаться от IP раннера**, не быть приватным/CGNAT.
   Жёсткое требование, а не «или», как сейчас.

Включённая проверка сертификата + реальный SNI = MITM-нода и «прозрачный прокси»
отваливаются автоматически.

Ключи, которым реально нужен `allowInsecure=1`, идут **не в мусор, а во вторую корзину**
(`tier: insecure`) с пометкой в отчёте — их можно публиковать отдельным файлом.

### Стадия 3 — качество

- Скачивание **2–5 МБ** с быстрого CDN. Скорость считается по устоявшемуся участку:
  первые 200 мс (TCP slow start) отбрасываются. **Порог применяется реально.**
- Латентность — **TTFB через прокси**, медиана из 3 замеров + джиттер.
  Именно по ней идёт сортировка выдачи.
- Ноды с исчерпанной квотой (хендшейк проходит, данные обрываются на ~200 КБ)
  ловятся именно здесь.

### Стадия 4 — стабильность ⭐⭐ *(того, чего сейчас нет вообще)*

**Внутри прогона:** 3 лёгкие пробы `204` с интервалом 30–60 с. Требуется ≥ 2 из 3.

**Между прогонами:** `state/history.jsonl.gz` — по отпечатку хранится EWMA успешности
за последние ~20 прогонов:

```jsonc
{"fp":"a3f9…","ok":18,"fail":2,"ewma":0.91,"runs":20,"last_ok":"2026-07-26T08:41:00Z","streak":5}
```

Правила публикации:
- `ewma >= 0.6` **и** успех в текущем прогоне;
- новый ключ публикуется только после **2 успешных прогонов подряд** —
  «повезло один раз» больше не проходит;
- записи, не встречавшиеся 7 дней, вычищаются.

Это превращает снимок удачи в реальный рейтинг и решает дефект #11.

### Стадия 5 — обогащение и классификация

- Страна + ASN — из **локальной GeoLite2 mmdb** вместо `ip-api.com` по запросу на ключ
  (текущие 342 `XX` — это ровно рейт-лимиты). Офлайн, мгновенно, без лимитов.
- Метки: датацентр / резиденциал, CDN, поддержка UDP, IPv6, WARP.
- Опционально — доступность YouTube / Telegram / Discord отдельными пробами.
- **Отсечение по exit IP выключено** (было: максимум 5 на адрес). Замер на боевых данных показал, что за одним выходным шлюзом стоит до 35 разных входных серверов, а на одном сервере — до 5 разных учёток; и то и другое даёт независимую живучесть, а отсечение выбрасывало уже проверенные рабочие ключи.
  Убирает те самые 527 ключей на `152.233.53.89`.

## 6. GitHub Actions

Три джоба вместо одного — обход лимита времени и 8× пропускной способности:

```
collect  →  скачать подписки, распарсить, дедупнуть, нарезать на 8 шардов  →  artifact
check    →  matrix [1..8], каждый проверяет свой шард                      →  artifacts
publish  →  слить, применить историю, записать файлы, один коммит
```

- `concurrency: { group: checker, cancel-in-progress: true }` — параллельные прогоны
  не дерутся за push.
- `timeout-minutes` на каждый джоб.
- Кэш: Go build cache, GeoLite2 mmdb, ETag подписок.
- Push с `git pull --rebase` и ретраем при конфликте.
- Коммит-сообщение с реальной статистикой; **вывод детерминированный** (случайная
  строка `announce` сеется датой) → диффы читаются.
- Расписание — как сейчас: каждые 3 часа, плюс `workflow_dispatch`.

**Оценка времени:** 19070 ключей → ~8000 после дедупа → ~4000 после L4 →
полный чек за **5–8 минут** на 8 шардах.

## 10. Известные ограничения и дорожная карта

### 10.1 Проверка идёт из дата-центра

Раннеры GitHub — это IP Azure. Отсюда:
- ноды, блокирующие датацентровые IP или с гео-фильтром, ложно помечаются мёртвыми;
- ноды, живые из Azure, могут не работать у пользователя в РФ (блокировки по
  IP/SNI/протоколу на стороне провайдера).

Чекер измеряет **«работает из дата-центра»**, а не «работает у пользователя».
Частично компенсируется исторической репутацией и учётом «белых» ASN.

### 10.2 Будущее: локальный запуск с ПК

Полностью проблема решается запуском проверки из целевой сети. Архитектура закладывается
под это **уже сейчас**, чтобы потом ничего не переписывать:

- один **статический бинарь без внешних зависимостей** (Xray встроен библиотекой,
  скачивать нечего) → одинаково работает на Windows и Linux;
- все пути через `filepath`, никакой Linux-специфики;
- выходная папка и путь к конфигу — флагами CLI;
- режим `check` умеет работать автономно и сохранять результат в JSON;
- формат `state/history.jsonl.gz` одинаковый локально и в CI → результаты локального
  прогона можно влить в общую историю.

Когда дойдут руки: `checker.exe check --shard=all --out=./result` на домашнем ПК,
результат мержится с CI-историей. Отдельный маркер `source: local` в записях истории,
чтобы различать «работает из дата-центра» и «работает из РФ».

### 10.3 Строгая проверка TLS

Отсекает легитимные ноды с самоподписанными сертификатами. Они не выбрасываются,
а попадают в корзину `tier: insecure` и публикуются отдельным файлом.
