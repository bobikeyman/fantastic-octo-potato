# 🐶 BobiVPN Checker

**Проверщик VPN-ключей, который не врёт.**

Собирает ключи из подписок, прогоняет через Xray-core и публикует только те,
что реально работают — с историей репутации, а не по одному удачному запросу.

## Зачем это

Обычный «чекер» подписок делает одну проверку через прокси и, если что-то ответило,
считает ключ рабочим. На практике так в выдачу попадает мусор.

Замер на выхлопе типичного такого чекера — 5196 «рабочих» ключей:

| Что не так | Сколько |
|---|---:|
| Скорость ниже собственного объявленного порога | **4138 (80%)** |
| Скорость ровно 0 — тестовый файл не скачался вообще | 232 |
| Выходной IP не менялся: это не прокси | 162 |
| Страна не определилась | 342 |
| Уникальных выходных IP из 5196 ключей | **1414** |
| Ключей, ведущих на один и тот же IP `152.233.53.89` | **527** |

Причины простые: выключена проверка TLS-сертификата, HTTP-403 засчитывается за успех,
объявленный порог скорости не применяется, скорость меряется на файле в 1 КБ,
а SOCKS-порты между параллельными проверками наезжают друг на друга.

BobiVPN Checker закрывает каждый из этих пунктов.

## 🔬 Как устроена проверка

Шесть стадий. Ключ обязан пройти все.

### 0 · Нормализация и дедуп

Ссылка разбирается в каноническую структуру, все query-параметры раскодируются
(`path=%2Fws%2Flink` → `/ws/link`). Считается **отпечаток** — SHA-256 от адреса,
учётных данных и транспорта, **без `#имени`**.

> Один и тот же сервер под десятком разных названий — это один ключ.
> Дедуп по полной строке ссылки, как делают наивные чекеры, множит работу втрое.

Здесь же отсеивается заведомо нерабочее: REALITY без `pbk` или с ключом неверной длины,
`sid` не в hex, `xtls-rprx-vision` без TLS или поверх WebSocket, VMess с `alterId > 0`,
приватные и CGNAT-адреса, устаревшие шифры Shadowsocks.

### 1 · L4-фильтр

TCP-дозвон с таймаутом 3 с. Результат кэшируется по `IP:port` — один мёртвый эндпоинт
хоронит все ключи на него разом. Домены за CDN не отсеиваются: там отвечает edge, а не нода.

### 2 · Настоящая проверка прокси ⭐

Через `core.Dial`, **с включённой проверкой TLS-сертификата**:

1. `cp.cloudflare.com/generate_204` → строго **204 и пустое тело**. Не 200, не 403, не редирект.
2. `www.gstatic.com/generate_204` → то же самое. Два разных ASN обязаны ответить.
3. `cloudflare.com/cdn-cgi/trace` → exit IP, colo и признак WARP одним запросом.
4. **Выходной IP обязан отличаться** от адреса раннера и не быть приватным.

Включённая проверка сертификата — это защита от нод, которые подменяют трафик:
такая нода не сможет предъявить валидный сертификат для `cloudflare.com` и отвалится сама.

Ключи, которым реально нужен `allowInsecure=1`, не выбрасываются — они уходят
в отдельную корзину `tier=insecure`.

### 3 · Качество

Скачивание 3 МБ; скорость считается по устоявшемуся участку — первые 200 мс
TCP slow start отбрасываются. **Порог применяется на самом деле.**
Латентность меряется как TTFB **через прокси** (медиана из трёх замеров) — по ней
и сортируется выдача. Ноды с исчерпанной квотой обрываются на этой стадии.

### 4 · Стабильность ⭐⭐

**Внутри прогона:** три лёгкие пробы с интервалом 45 с, нужно ≥ 2 успешных.

**Между прогонами:** `state/history.jsonl.gz` хранит EWMA успешности по каждому отпечатку.
В выдачу попадает ключ с `ewma ≥ 0.6`, а новый ключ публикуется только после
**двух успешных прогонов подряд**.

> Именно это отличает рейтинг от снимка удачи. Ключ, случайно ответивший один раз,
> в подписку не попадёт.

### 5 · Обогащение

Страна и ASN — из локальной базы GeoLite2, офлайн и без лимитов
(запросы к `ip-api.com` по одному на ключ упираются в rate limit — отсюда сотни
ключей с неопределившейся страной у наивных чекеров).

Финальный отбор: **не больше 5 лучших ключей на один выходной IP**.

## 🧩 Почему Xray-core

Распределение параметров в реальном пуле подписок:

```
security=reality      52%
flow=xtls-rprx-vision 44%     XTLS Vision — референсная реализация в Xray
type=raw              398     Xray-нейминг сырого TCP
type=xhttp             54     транспорт, которого нет у большинства конвертеров
```

Ядро подключено **как Go-библиотека**, а не запускается подпроцессом:

```go
inst, _ := core.New(cfg)
conn, _ := core.Dial(ctx, inst, dest)   // net.Conn через прокси
```

| | подпроцесс + SOCKS | библиотека |
|---|---|---|
| SOCKS-порты | нужны, возможны гонки | **не нужны вообще** |
| Готовность | `sleep(3)` наугад | `core.Start()` вернул `nil` |
| Зависимости в CI | скачать и распаковать Xray | **всё в бинаре** |
| Точность таймингов | плюс погрешность SOCKS-хопа | замер прямо на `Dial` |
| Windows | отдельный бинарь и пути | работает как есть |

Последнее важно: чекер собирается в один статический бинарь, поэтому позже его можно
будет запускать не только в CI, но и локально — из целевой сети (см. «Ограничения»).

**Не поддерживается:** `hysteria2`, `tuic`, `anytls` — их нет в Xray-core.
В реальном пуле это 0.2% ключей; они отбраковываются с пометкой `unsupported_protocol`
и попадают в статистику. Интерфейс движка абстрактный — второе ядро для них
можно добавить, не трогая пайплайн.

## 🚀 Локальный запуск

```bash
git clone https://github.com/bobikeyman/fantastic-octo-potato
cd fantastic-octo-potato

go build -o checker ./cmd/checker      # сборка
go test ./...                          # тесты (офлайн, сеть не нужна)
```

Проверка ключей идёт в GitHub Actions. Локально доступен разбор подписки без сети:

```bash
./checker parse --file testdata/corpus.txt --stats
```

Все пороги — в [`configs/checker.yaml`](configs/checker.yaml).

## ⚙️ CI

Три джоба вместо одного — обход лимита времени и восьмикратная пропускная способность:

```
collect  →  скачать подписки, разобрать, дедупнуть, нарезать на 8 шардов
check    →  matrix [1..8], каждый проверяет свой шард
publish  →  слить, применить историю, записать файлы, один коммит
```

Приватные подписки кладутся в секрет `SUBSCRIPTION_URLS`,
публичные — в [`subscriptions.txt`](subscriptions.txt).

## ⚠️ Ограничения

**Проверка идёт из дата-центра.** Раннеры GitHub — это адреса Azure. Поэтому:

- ноды, блокирующие датацентровые IP или с гео-фильтром, ложно помечаются мёртвыми;
- ноды, живые из Azure, могут не работать у пользователя в РФ — блокировки
  по IP, SNI или протоколу происходят на стороне его провайдера.

Чекер измеряет **«работает из дата-центра»**, а не «работает у вас».
Частично это компенсирует история репутации. Полностью решается запуском
из целевой сети — под это архитектура заложена (один бинарь без внешних
зависимостей, общий формат истории), но запуск ещё не реализован.

**Строгая проверка TLS** отсекает ноды с самоподписанными сертификатами.
Они не выбрасываются, а публикуются отдельно с пометкой `tier=insecure`.
